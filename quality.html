Quality and monitoring

Every load is checked before the data is released. A failed check blocks the load and tells the on-call person what broke.

CheckWhat it asksExample ruleIf it fails
FreshnessDid the data arrive on time?Newest event is under 30 minutes oldAlert, show a "data delayed" banner
CompletenessIs anything missing?Required columns under 0.5% null; row count matches sourceBlock load, alert
SchemaDid the shape change?Columns and types match the contractQuarantine file, notify the data owner
VolumeIs the size normal?Within 30% of the same weekday averageHold for review
FailuresDid a job crash?Any non-zero exit, 3 retriesPage on-call
Downstream healthAre dashboards and feeds healthy?Extract refresh succeeded; feed lag under 15 minutesAlert the dashboard owner

Example: volume anomaly check

def volume_ok(today, same_weekday_avg, tolerance=0.30):
    low = same_weekday_avg * (1 - tolerance)
    high = same_weekday_avg * (1 + tolerance)
    return low <= today <= high

if not volume_ok(rows_loaded, baseline):
    hold_release("fact_ad_impression")
    send_alert("Volume outside normal range", rows_loaded, baseline)

Support and handover

  • Each alert links to a short runbook: what it means, how to check, who owns the fix.
  • Every delivered data set has a data dictionary and a one-page owner note.
  • Root-cause notes are written after each incident and turned into new checks.
