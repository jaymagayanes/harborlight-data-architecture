Data model

A star schema with one fact table per business event and shared dimensions, so every team counts things the same way.

TableTypeGrain (one row per)Key columns
fact_ad_impressionFactAd shown to a viewerdate_key, campaign_key, content_key, customer_key, revenue
fact_subscription_eventFactStart, renewal, upgrade or canceldate_key, customer_key, plan_key, event_type, amount
fact_viewing_sessionFactViewing sessiondate_key, customer_key, content_key, minutes_watched
dim_date, dim_customer, dim_campaign, dim_content, dim_planDimensionCalendar day, customer, campaign, title, planSurrogate key plus business key. Customer history kept with start and end dates.

Layers

  • Staging: one table per source table, correct data types, duplicates removed.
  • Core: the star schema above. Business rules live here once.
  • Marts: pre-joined views for finance, ads and growth, so dashboards stay fast.

Performance choices

  • Monthly partitions on the large fact tables, so queries read only the months they need and old months can be archived cheaply.
  • Columnstore index on facts for scans and aggregates. Narrow indexes on dimension keys for lookups.
  • Incremental loads by partition, with a quick rebuild path for any single month.
CREATE PARTITION FUNCTION pf_month (date)
AS RANGE RIGHT FOR VALUES ('2026-01-01','2026-02-01','2026-03-01');

CREATE PARTITION SCHEME ps_month
AS PARTITION pf_month ALL TO ([PRIMARY]);
